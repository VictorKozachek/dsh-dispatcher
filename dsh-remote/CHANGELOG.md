# Changelog

Формат: версия — дата — что изменилось. Версия плагина — `dsh-remote/package.json`.

## 0.3.3 — 2026-11-24

Спека 011 «Надёжность мессенджеров»: меньше протухших сообщений, понятная реакция
на клик по закрытому вопросу, напоминания без засорения чата и сторож канала.

- **Компактная шапка и имя сессии (083).** Шапка вопроса — `проект · task ·
  время · до`; длинное имя сессии больше не обрезается, а идёт отдельной строкой
  с переносом по словам.
- **Снятие вопроса одной операцией (084).** TTL/аборт/рестарт правят сообщение
  один раз: текст «⌛ вопрос снят …» и пустые кнопки (Telegram
  `inline_keyboard: []`, MAX `attachments: []`). Предварительная пометка «ждёт
  ответа» убрана; журнал `question.expired {ttl|aborted|restart}`,
  `question.closeFailed`, повтор с backoff на 429; `recover` чистит
  `pending`/`questions`.
- **Клик/текст по закрытому вопросу (085).** Вместо тишины — видимая подсказка
  («этот вопрос уже снят — ответьте в GUI» / «ответ уже дан»), без спама (LRU по
  `chatId:messageId`); журнал `answer.rejected {unknown|expired|already-answered}`.
  Текст реплаем на снятое сообщение получает короткий ответ в чат, чужое
  сообщение не редактируется.
- **Сторож канала (086).** N минут тишины в апдейтах или серия ошибок поллинга →
  перезапуск транспорта с backoff 1/2/3 с; после 3 неудач — `channel.failed`, без
  бесконечных попыток. `/remote status` показывает «последний апдейт N мин
  назад», перезапуски и последнюю ошибку; сторож учитывает открытый `pending` и
  in-flight доставку и не перезапускает канал во время отправки.
- **Напоминания и TTL-пометки правкой (087).** Напоминание меняет существующее
  сообщение (кнопки сохраняются); только при невозможности правки — одно новое с
  пометкой «(обновление)», не поток. Журнал `question.reminder {via:
  edit|new|dropped}`.

Ограничения: в режиме `mirror notify` плашка вопроса в GUI по-прежнему не
убирается сама — хосту нужны `settle/cancel` (обращение DSH #13932);
`bash`-подтверждения по умолчанию остаются локальными в GUI, включаются
`/remote approvals mode all`; полная горячая перезагрузка транспортов/ответчика
не входит и в этот релиз.

## 0.3.2 — 2026-11-23

- **Имя сессии в шапке вопросов (068, 069, 078).** Базовая фича: имя берётся из
  API сессии, при его отсутствии — из кэша проекций; в шапке оно заменяет id
  пресета (`standard`), модель вопроса хранит `sessionTitle`. Имя ищется сначала в API сессии,
  затем в кэше проекций; `context.resolve` пишет маскированные id, источник и
  причину, фолбэк по `session.id`, а контекст целиком передаётся в
  `createQuestions` — в шапке больше не печатается пресет `standard` вместо имени
  («Оркестратор»).
- **Документация зеркального режима (067).** `docs/user-guide.md`, CONCEPT §7.1 и
  матрица приёмки описывают `mirror` (full/notify), кто принимает ответ и что
  происходит с сообщением/GUI-плашкой.
- **Панель «Удалённое управление»: история (070, 045).** История вопросов за
  24 часа из `log.jsonl`: статусы «доставлен / ошибка доставки / отвечен / не
  сопоставлен / снят», раскрытие деталей, чтение ротаций `.1…5`, только чтение;
  отдельно фильтр по проекту и подписи политики подтверждений (074, 076).
- **Зеркало: GUI → MAX (071).** Ответ в GUI гасит сообщение в мессенджере
  («✅ Отвечено в GUI»), ошибка закрытия не ломает ответ и пишется в журнал;
  поздний клик — `answer.dropped {reason:"gui"}`.
- **Зеркало: MAX → сессия (073).** В `notify` ответ из канала завершает
  tool-call (сессия не висит), сообщение закрывается «✅ Отвечено (передано в
  сессию)»; повторный/поздний ответ — `dropped {reason:"already-answered"}`.
- **Зеркало: без ложного приглашения печатать (072).** В `notify` больше нет
  «Другой ответ…» и подсказки печатать текст: сообщение говорит «ответьте в GUI
  (или нажмите кнопку)»; в `full`/`remote-only` поведение прежнее.
- **Подтверждения: видимая политика и управление (074).** `/remote approvals`
  показывает `tools`, `denyRemote`, `onTimeout`, ttl и последнее решение с
  причиной; `allow|deny <tool>` меняет политику в `state.json` без перезапуска;
  опасный `allow` требует `--force` и предупреждает; причина GUI-решения
  (`deny-remote`/`tool-not-allowed`) пишется в аудит; безопасный дефолт сохранён.
- **Диагностика ранних выходов ответчика (075).** `question.skipped` с причиной
  (`aborted`/`broker-unsupported`/`mode-disabled`/`no-transport`), scope,
  маскированными id и пресетом; одно событие на запрос; `no-questions` не шумит;
  противоречие «global=true, а режим выключен» помечается `level:"warn"`.
- **Контекст событий журнала (076, 081).** `sessionId` (маска), `workspace`
  (basename) и `preset` пишутся с первого события вопроса; `record()` не
  выбрасывает эти поля; полные пути и тексты ответов не попадают в журнал;
  фильтр истории по проекту работает на живых данных.
- **Онбординг подтверждений и режимы (077).** `/remote connect` спрашивает один
  раз: «Да, всё» / «Только безопасные» / «Всё только в GUI»; режимы
  `safe|all|gui-only` в состоянии, `/remote approvals mode …` переключает без
  перезапуска; явный `deny` сильнее `all`; предупреждение для `all` — в статусе.
  Ограничение: предупреждение появляется и в статусе, и в ответе команды, но
  владелец может включить `all` осознанно — дефолт остаётся безопасным.
- **Имя сессии в подтверждениях (080).** `marksOf` отдаёт весь контекст, и
  `RemoteApproval` рендерит имя сессии в шапке подтверждения, а не пресет.
- **Горячая перезагрузка `present`/`i18n` и `/remote reload` (079).** Правки
  шапки, тела, кнопок и словарей подхватываются следующим вопросом/командой без
  перезапуска приложения; загрузчик проверяет mtime и кэширует, битый модуль не
  роняет плагин (остаётся прошлая версия + `hot.error`), `config.hotReload:false`
  выключает перечитывание. Ограничение: полный re-apply ответчика/транспортов
  (шаг 2) не входит в этот релиз.
- **Журнал и фильтр истории (081).** `record()` действительно пишет
  `workspace`/`sessionId`/`preset`; старые строки без полей читаются как раньше.
- **Ограничения зеркала.** В режиме `notify` плашка вопроса в GUI не исчезает
  сама после ответа из мессенджера: хосту нужны `settle/cancel` (обращение в
  Discussions DSH #13932). Подтверждения `bash` и других опасных инструментов
  по умолчанию остаются локальными в GUI; включаются явно через
  `/remote approvals mode all` или `allow --force`.

## 0.3.1 — 2026-11-17

- **Журнал в файл (051).** Рабочий `~/.dsh/remote-control/log.jsonl` с
  событиями `question.send/sent/error`, `answer.received/unmatched`,
  `pairing.*`: путь, `shortId`, транспорт, HTTP-код; токены и тексты ответов
  маскируются (`customLength` вместо текста), ротация 5 МиБ × 5, `logFile: false`
  и `DSH_REMOTE_LOG_FILE`.
- **Журнал виден ответчику (056).** Сервис публикуется через `deps.expose`, а не
  только `ctx.get`: файл действительно пишется, `status`/`doctor` показывают
  путь журнала.
- **MAX после `/remote connect` (052).** Убран ранний `return` для «не
  telegram»: ветка `max` в `ensureTransport` достижима, канал создаётся и
  стартует, вопрос уходит в MAX. При смене привязки/токена транспорт
  пересоздаётся, при пропаже токена старый поллер останавливается.
- **MAX legacy-хост (054).** Апдейты с `update_type` разбираются наравне с v2
  (`type`): кнопки и свободный текст доходят до вопроса, pairing находит код.
- **`/remote on --all` и `status` (057).** `on/off --all` снимают спорящие
  точечные исключения (`global=true` больше не перекрывается
  `workspaces[x]=false`), `status` показывает глобальное значение и scope
  перекрытия; точечные `on/off` после `--all` снова перекрывают.
- **`doctor` на MAX-only (053).** Секреты проверяются по активной привязке:
  MAX-only зелёный, telegram-only не требует MAX-токен, привязка без своего
  токена — `fail`, токен отключённого канала — `info`.
- **Лимиты текста (055).** Регресс-тесты: MAX никогда не отправляет `text`
  длиннее 4000 (включая длинный `<pre>`), Telegram по-прежнему режет по 4096.
- **MAX «Другой ответ» (061).** Клик больше не удаляет запись вопроса: текст
  принимается, отдельное приглашение с заголовком сохраняется, «Показать ещё» не
  теряет вопрос; TTL снимает зависший вопрос.
- **Полировка формата сообщений (047; код вошёл в 0.3.0, в changelog 0.3.0
  пропущен).** Компактная шапка, `truncateLines` с «…ещё N строк», корректный
  `renderHtml` с `pre`/`code`, одна подсказка, ссылка на ветку/дерево в шапке,
  снапшоты формата.

## 0.3.0 — 2026-11-11

- **Один активный канал (038, 042).** Подключение нового канала отключает прежний;
  открытые вопросы старого канала снимаются, ответ и закрытие идут в канал, где
  вопрос был доставлен; `status` показывает секрет и состояние активного канала
  (Telegram / MAX / Relay). Переключение проверено на локальном стенде с реальным
  relay и RelayKit через HTTPS-туннель; живой Telegram-чат снят по решению
  оркестратора — это проверка владельца, а не автотест.
- **MAX через `/remote connect` (039).** Токен, pairing-код, привязка и запуск
  канала без перезапуска профиля; pairing через long polling.
- **Локальный релей (040) и HTTPS-туннель (041).** Запуск `dsh-relay` на
  `127.0.0.1:8080`, миграции на старте, smoke-тест, плагин → релей без телефона;
  внешний доступ проверен через SSH-туннель `localhost.run` клиентом RelayKit по
  HTTPS (cloudflared quick tunnel в этой сети давал 502/530; Tailscale —
  документированный вариант, вживую не проверялся). UI-приложение на телефоне не
  проверялось — это проверка владельца.
- **Исправления живой приёмки.** Сервисы берутся через `ctx.get` (cordis запрещает
  прямой доступ без `inject`); ленивый поиск секретов, когда `ctx.credentials`
  монтируется позже плагина; канал поднимается повторами после старта; поле ввода
  (`force_reply`) для вопросов без вариантов; тесты изолированы от живого
  состояния (`DSH_HOME`).
- **Эксплуатация (036).** Soak-тест на 1000 вопросов, RUNBOOK с SLO и покрытием
  `doctor`-fail; `log.jsonl` ротируется по единому пределу 5 МиБ (`rotate.js`).

## 0.2.0 — 2026-11-03

- Установщик: `--update` (сравнение версий из профиля и пакета), `--rollback <version>`
  из кэша предыдущих версий, проверка совместимости (`node --check` + schemaVersion
  состояния 032) перед установкой.
- Аудит решений, политика подтверждений (allowlist/denyRemote/TTL), очередь и
  роутинг подтверждений, гибрид с GUI, метрики `/remote stats`, doctor 2.0,
  ротация журналов и `/remote vacuum`.
- Состояние: схема v2 и миграция v1 → v2 с бэкапом.
