# dsh-remote

Плагин DSH: удалённое управление вопросами агента — вопрос из
`ask_user_question` уходит в мессенджер (Telegram, затем MAX), а ответ
возвращается в ту же сессию результатом инструмента, с маркировкой рабочего
каталога, задачи и роли. Не форк и не патч ядра: плагин встаёт в штатный
waterfall `user-questions/request`.

Сейчас здесь только каркас (задача 001): пакет поднимается в профиле, читает
`config` и держит реестр фич (`lib/features.js`). Концепция —
[docs/CONCEPT.md](../docs/CONCEPT.md), спека — `.kanban/specs/001.md`.

## Как включается и где состояние

`dsh plugin --profile <профиль> add <путь>/dsh-remote`: пакет объявляет
`dsh.bundle.patch`, в профиле появляется ряд `ui-remote` с `name: 'dsh-remote'`
(см. `cordis.patch.yml`) — руками профиль не правится, а включение режима живёт
в состоянии: `/remote on|off`.

`~/.dsh/remote-control/state.json` (атомарно, chmod 600) и `log.jsonl` без
секретов; токены мессенджеров — только через `ctx.credentials`, в git их нет.

Поставить в профиль: `bin/install-remote.sh --dry-run` (план), затем
`bin/install-remote.sh` (профиль `web` или `--profile desktop`). Скрипт
идемпотентен и отказывается ставить пакет, если в профиле остался ручной ряд
`ui-remote` — иначе плагин смонтируется дважды.

Диагностика: `/remote doctor` — список пунктов `ok/warn/fail` с подсказками
(токен и его источник, `getMe`, конфликт поллеров по lock, последняя ошибка
канала, состояние и права `state.json`, версия плагина).

Тесты: `node --test dsh-remote/test`; на Node ≥ 22 надёжнее
`node --test dsh-remote/test/*.spec.js`.

## Панель «Удалённое управление»

Правая панель DSH Web → «+» → **Удалённое управление** (тип таба
`dsh-remote-panel`, приоритет `extension`). Панель показывает:

- **статус канала**: поднят ли транспорт (`канал поднят` / `канал не поднят`) и
  откуда он — из привязки `/remote connect` или из `config.telegram` профиля;
- **привязка**: имя бота (`@…`), без токена и без id чата в тексте;
- **режим**: «все проекты», включённые воркспейсы (только `basename`) и сессии
  (сокращённый id);
- **открытые вопросы**: короткий id, задача/роль/воркспейс и дедлайн —
  отсортированы по близости дедлайна;
- **журнал**: последние 20 строк `log.jsonl` (только `время событие shortId`);
- кнопки **«Тест»** (отправить тестовый вопрос в канал) и **«Обновить»**;
  **«Снять»** у вопроса.

Кнопка «Снять» в этой сборке **read-only**: host-канал вызывает
`remoteReliability.dismiss`, если такой метод у сервиса есть, иначе панель честно
пишет «снять вопрос нельзя: `/remote status` в сессии», а не делает вид, что
сняла. Устойчивость (задача 008) пока не умеет снимать отдельный вопрос — это
отдельная доработка, после неё кнопка заработает без правок клиента.

### Как это устроено

Состояние и журнал лежат **вне** воркспейса (`~/.dsh/remote-control/`), а
клиентская половина читает только воркспейс, поэтому снимок для панели собирает
хост и отдаёт его по RPC:

- `lib/client.js` — клиентский бандл (`window.__ModuleLoader__.load`, React из
  оболочки, без сборщика и JSX), объявлен как `exports["./client"]` и
  `dsh.client { platform: "web", inject: [...] }`;
- `lib/panel.js` — чистая логика снимка: чтение состояния и журнала,
  нормализация, сортировка вопросов по дедлайну и **очистка секретов и полных
  путей** (пути заменяются на `basename`, токены — на `<redacted>`);
- `lib/host-channel.js` — RPC-служба `remotePanel` (`snapshot`, `dismiss`,
  `test`) с маркерами Typert того же контракта, что у
  `dsh-kanban/lib/card-actions.js`; клиент присылает только `{}` или
  `{shortId}` — никаких путей и команд;
- `lib/features/panel.js` — регистрация канала в контексте плагина.

Если в сборке нет сервиса `sidebarRightTabs` (старая версия DSH), панель не
регистрируется, в лог уходит «панель недоступна в этой сборке» — плагин и
хост-канал продолжают работать. Обновление панели — раз в 3 секунды; фид
изменений не видит записей из bash, поэтому опрос.

Тесты панели: `node --test dsh-remote/test/client.spec.js` — форматирование
статуса, фильтрация журнала и сортировка вопросов по дедлайну (без DOM и без
браузера).

## MAX (второй канал)

`lib/transport/max.js` реализует тот же контракт `QuestionTransport`, что и
Telegram: вопрос с кнопками, ответ кнопкой или текстом, правка сообщения. Включается
`config.max` в строке плагина профиля.

### Что нужно от человека

Платформа MAX пускает ботов только **юрлицам, ИП и самозанятым — резидентам РФ**
(физлицу бота не завести: нужен верифицированный профиль организации). Порядок:

1. Зарегистрироваться на [business.max.ru/self](https://business.max.ru/self) или в
   мини-приложении «MAX для бизнеса», верифицировать профиль.
2. Создать чат-бота (квота: 5 ботов на организацию/ИП, 2 — на самозанятого),
   пройти модерацию (до 48 часов по рабочим дням). Никнейм генерируется
   автоматически (`idИНН_bot`) и не меняется.
3. Взять **токен** в business.max.ru/self → «Чат-боты» → ⋮ → «Настройки»
   (или командой «Получить токен» у бота «MAX для бизнеса»).
4. Узнать `chat_id`/`user_id` получателя: `GET /chats` больше не поддерживается.
   Человек пишет боту `/start`, после чего id берутся из `GET /updates`
   (`update.user.user_id` / `update.chat.chat_id`) — это самый надёжный ручной
   путь. Если транспорт уже запущен, событие `bot_started` попадает в лог, а id
   запоминаются в `transport.detected` (используется для диагностики; в
   `config.max` их пока вписывают руками).
5. Положить токен в секреты под именем `DSH_REMOTE_MAX_TOKEN` (или указать свой
   `tokenRef` в `config.max`) и включить режим `/remote on`.

### Как включить (профиль)

```yaml
- id: ui-remote
  name: dsh-remote
  config:
    max:
      tokenRef: DSH_REMOTE_MAX_TOKEN
      chatId: 123456789        # или userId для личного диалога
      allowedUserIds: [987654321]
```

Транспорт работает long polling (`GET /updates`): токен — в заголовке
`Authorization`, `marker` сохраняется в `max-marker.json` рядом с состоянием
(`~/.dsh/remote-control/`) с правами 600 и переживает перезапуск — иначе MAX без
`marker` вернул бы только последнее обновление. Лимиты платформы —
2 сообщения/сек и 2 правки/сек в чат, поэтому отправка и правки идут через
троттлинг, а на 429/503 — свой backoff с джиттером (`retry_after` MAX не
документирует). Нажатие кнопки приходит как `message_callback` и одним вызовом
`POST /answers` подтверждается и правит сообщение; свободный текст —
`message_created`. Повторы обновлений отбрасываются по композитному ключу
`sha256(chat_id, тип, callback_id|mid, timestamp)` — глобального `update_id` у MAX нет.

### Ограничение webhook

MAX считает webhook единственным production-режимом, но требует публичный
HTTPS:443 с валидным сертификатом (самоподписанные запрещены с 25.05.2026), а DSH
не умеет слушать внешний адрес. Поэтому `webhookUrl` в `config.max` **не
запускает** транспорт: в лог уходит внятная ошибка с предложением long polling
или туннеля. Это осознанное ограничение карточки 011, а не молчание.

## Каналы проектов

Разные проекты можно развести по чатам (и топикам форумов в Telegram), чтобы
вопросы не смешивались:

```
/remote channel alpha 100 7     # проект alpha → чат 100, топик 7 (forum topic)
/remote channel beta 200        # проект beta → чат 200
/remote channel list            # какие каналы у каких проектов
/remote channel remove alpha    # вернуть проект в общий чат
```

Ключ проекта — `basename(cwd)` сессии; канал хранится в `state.json`
(`channels: {"<проект>": {"<транспорт>": {chatId, threadId?}}}`) и не является
секретом. Канал задаётся **на транспорт**: у Telegram и MAX разные chatId, и
telegram-чат не должен уезжать в MAX. По умолчанию — транспорт привязки
(`/remote channel alpha 100 7 --transport=telegram`), а канал другого транспорта
добавляется отдельно (`--transport=max`).
`/remote status` показывает раскладку, а вопрос без своего канала идёт в общий чат
привязки (в шапке видно проект из 006).

Чужой `chatId` (не совпадающий с привязанным) отвергается: бот мог не быть в том
чате, и тогда ответы не придут. Если бот действительно добавлен — повторите с
`--force`. У групп и супергрупп Telegram `chat_id` отрицательный (форумы с
топиками тоже), такой тоже принимается — например
`/remote channel forum -1001234567890 7`. Имя проекта нормализуется до
`basename`, поэтому `/remote channel /home/vic/alpha 100` и сессия с cwd
`/home/vic/alpha` совпадут.

Чаты проектов входят в allowlist транспорта **динамически**: добавили канал —
ответы из него принимаются сразу, удалили — чат снова чужой (перезапуск не нужен).
Сообщения из прочих чатов по-прежнему игнорируются.

Про pairing: `/remote connect` привязывает **общий** чат (он же default для
проектов без своего канала); каналы проектов настраиваются после этого командой
`/remote channel`. Отдельного pairing-кода на каждый проект нет — это осознанное
решение: код подтверждает человека и выдаёт `deviceToken`, а проект выбирается
каналом; ответы из чатов проектов принимаются, потому что они входят в allowlist.

Уведомления доски (задача 014) тоже пойдут в канал проекта — маршрутизация
подключается в `features/notify.js` после слияния 014 (`resolveChannel` уже готов).

## Гибридный режим (мессенджер → GUI)

`/remote on --hybrid` включает режим «человек у ноутбука, но вопрос виден и в
телефоне»: вопрос публикуется в мессенджер, и если ответа нет `hybrid.waitMs`
(по умолчанию 20 с), вызывается `next()` — вопрос уходит в GUI, а сообщение в
мессенджере **остаётся открытым**. Поздний ответ из мессенджера не теряется: он
доставляется в сессию как уточнение `sessionController.prompt({mode: "steer"})`
со свежим `AbortSignal` и новым `requestId`, а сообщение закрывается как
отвеченное. Выключение — `/remote off --hybrid` или `--no-hybrid`; `status`
показывает «гибрид: вкл, ждём 20 с» и метрику «в GUI N, ответов из телефона
после GUI M».

Ограничения (осознанные, закреплены тестами):

- **Пачка вопросов** отдаётся в GUI целиком и только если в ней ещё нет ответов:
  если один вопрос уже отвечен, остальным GUI не показываем (DSH вернул бы весь
  запрос вместе с отвеченным), они ждут ответа в мессенджере или TTL — в лог идёт
  «пачка уже частично отвечена, GUI не зовём».
- **Сбой доставки steer** (например, сессия уже закрыта): ответ остаётся
  принятым, сообщение не закрывается, в лог пишется причина; повторная попытка
  будет при следующем ответе из мессенджера. Авто-ретрая нет намеренно, чтобы не
  дублировать уточнение в сессию.

## Транспорт relay (свой сервер)

Плагин умеет ходить не только в Telegram/MAX, но и в **свой релей** по протоколу
v1 (`docs/relay/PROTOCOL.md`, сервер — задача 017). Для плагина это тот же
`QuestionTransport`: он не знает, на чём написан релей.

Конфиг в строке плагина:

```yaml
relay:
  url: https://relay.example
  tokenRef: DSH_REMOTE_RELAY_TOKEN   # ссылка на секрет, не значение
  deviceTokenRef: DSH_REMOTE_RELAY_DEVICE_TOKEN   # необязательно
  keyId: key-2026-11                              # задел под e2e (021)
```

Или интерактивно: `/remote connect` → «Relay (свой сервер)» → URL → токен агента
(`RELAY_AGENT_TOKEN` релея); токен сохраняется в `ctx.credentials` как
`DSH_REMOTE_RELAY_TOKEN`, в `state.json` попадает только URL. `/remote status`
показывает «релей: …, на связи/нет связи, ждёт ответа: N».

Что важно знать:

- **Плагин — агент, а не устройство.** Он публикует вопросы (`POST /v1/questions`)
  и читает ответы (`GET /v1/answers`), поэтому ему нужен токен *агента*.
  Pairing-код выдаёт токен телефону; этот токен не может публиковать вопросы
  (релей ответит `403`). Поэтому в `/remote connect relay` спрашивается токен
  агента, а не pairing-код — осознанное отличие от формулировки задачи.
- **Отправка идемпотентна:** повтор с тем же `id` вопроса обновляет запись на
  сервере (`ON CONFLICT(id)`), дубля нет.
- **Закрытие вопроса** в протоколе v1 не предусмотрено: `closeQuestion` снимает
  вопрос локально, сервер закроет его ответом или TTL. Кнопки рисует клиент
  релея, поэтому «снять кнопки» на стороне плагина нечего.
- **Ответы:** WebSocket `GET /v1/events` используется, если платформа умеет
  передать заголовок `Authorization` (в тестах — инжектируемый `wsFactory`).
  Иначе транспорт сразу работает long-poll'ом `GET /v1/answers?...&wait=25`;
  при разрыве WS — переподключение с backoff (1→30 с) и long-poll на время
  простоя. Ответ забирается HTTP-ом по `questionId` из события.
- **Секреты:** токен вырезается из всех сообщений (`redact`), pairing-код
  транспорт вообще не использует; в логах только id вопросов и коды протокола.

Тесты: `node --test dsh-remote/test/relay-transport.spec.js` — сеть, WebSocket,
таймеры и `sleep` инжектируются, реальных запросов нет: отправка и повтор,
локальное закрытие, long-poll, WS + переподключение, ошибка неверного токена,
отсутствие секретов в логах.
