# Спека 004: Удалённые подтверждения (approvals) и защита от простоя

Статус: нарезана (карточки 024–029).
Концепция: [docs/CONCEPT.md](../../docs/CONCEPT.md) §3, §8.
Основание: в DSH есть второй waterfall — `approval/request`
(`packages/interaction/user-approval/src/types.ts:85`,
`docs/subsystems/approval.md`:152 в чекауте DSH).

## Зачем

Вопрос — не единственная блокировка. Агент останавливается ещё и на
**подтверждении действия** (`approval/request`: можно ли запускать эту команду,
писать этот файл, вызывать этот инструмент). Исход закрытый:
`allowed-once | rejected | cancelled | unavailable`, и при `unavailable` вызывающий
**fail closed** — то есть без человека действие не выполняется. Для нас это тот же
простой: человек отошёл, а агент не может ни продолжить, ни отказаться осмысленно.

Отличие от вопросов принципиальное: тут решение **бинарное и опасное**. Ошибка
стоит дорого, поэтому политика важнее удобства.

## Требования

1. **Перехват** `approval/request` с `{ prepend: true }` (как у вопросов):
   режим включён → запрос уходит в канал человеку, ответ возвращается
   `ApprovalOutcome`; выключен → `next()` (штатное поведение DSH и GUI).
2. **Кнопки решения**: `Разрешить один раз` (`allowed-once`), `Отклонить`
   (`rejected`), `Не отвечать` (оставить GUI / `unavailable`). Никакого
   «разрешить всегда» в MVP — это дыра в безопасности.
3. **Политика по умолчанию — отказ по таймауту**: не ответили за TTL →
   `cancelled` (а не `allowed-once`). Конфиг `onTimeout: 'cancelled' | 'unavailable'`.
4. **Маркировка**: воркспейс, сессия, роль, инструмент (`toolName`), `callId`,
   причина (`reason`), время и дедлайн — как у вопросов (модель из 006).
5. **Аудит**: каждое удалённое решение пишется в журнал (кто, когда, что, канал,
   исход) и не содержит секретов; `approval/asked`/`approval/decided` DSH тоже
   остаются в логе сессии.
6. **Ограничение поверхности**: allowlist инструментов (`approvals.tools`),
   запрет удалённо подтверждать выбранные (`denyRemote`, например `git push`).
   Неизвестный инструмент → не показываем кнопки, отдаём GUI.
7. **Несколько подтверждений сразу**: очередь, нумерация, reply-привязка, ответ
   попадает в свой `callId` (роутинг из 007).
8. **Гибрид**: не ответили N секунд → запрос уходит в GUI (`next()`), поздний
   ответ из канала не переигрывает решение, а логируется.

## Вне скоупа

- «Разрешить навсегда» и правила по шаблонам команд (это отдельная политика
  безопасности, а не UX);
- plan-review (`ask_user_question` с `intent: plan-review`) — сейчас модель его не
  передаёт, вернёмся, когда DSH даст поле в схеме инструмента;
- мобильные приложения (уже есть 019/020, approvals пойдут через тот же транспорт).
