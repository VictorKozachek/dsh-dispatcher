## Задача

Команды `/remote` и привязка бота — вход в систему.

1. `dsh-remote/lib/store.js`: состояние на диске.
   - путь `~/.dsh/remote-control/state.json` (переопределяется env `DSH_REMOTE_STATE` — тесты),
     атомарная запись (tmp + `rename`), `chmod 600`, версия формата;
   - поля: `version`, `bindings` (transport, chatId, userId, botUsername, createdAt),
     `enabled` (`{ global: bool, workspaces: { [cwd]: bool }, sessions: { [id]: bool } }`),
     `recent` (кольцевой буфер последних вопросов), `pending`;
   - lock-файл `~/.dsh/remote-control/lock` (`wx`), чтобы два процесса не поллили один токен;
   - токен **не хранится**: `ctx.credentials` (`resolve`/`describe`/`set`/`unset`),
     ссылка — POSIX-имя (`credentialRef('DSH_REMOTE_TELEGRAM_TOKEN')`). Окружение
     главнее файла `~/.dsh/.credentials.yaml`, и тогда `describe().writable === false`
     — это надо показывать в `status`, иначе человек правит файл, а читается env.
2. `dsh-remote/lib/commands.js`: регистрация в `ctx.commands.register`:
   - `/remote connect` — пошагово через **локальный** `ctx.userQuestions.ask`
     (удалённый режим ещё выключен): транспорт (`Telegram`/`MAX`), токен,
     затем pairing-код (6 цифр, TTL 10 мин) — человек отправляет его боту;
     подтверждение привязки (chatId/userId) и вопрос «только этот проект / все проекты»;
   - `/remote on|off` — воркспейс текущей сессии (`cwd` из `ctx.sessions.get(agent.id)`),
     `--all` — глобально; `/remote status`, `/remote test` (тестовый вопрос),
     `/remote who`, `/remote disconnect`;
   - `handler` получает `invocation.agent` и `invocation.rawInput` — разбор аргументов
     простой и предсказуемый, неизвестная команда печатает справку.
3. Тесты: `test/store.spec.js` (атомарность, права, параллельная запись двух процессов
   не рвёт файл, битый JSON → дефолт), `test/commands.spec.js` (фейковый `ctx` с
   `commands`/`userQuestions`): connect проходит по шагам, неверный код отвергается,
   `on/off` меняет scope, `status` показывает привязку.

## Критерии готовности

- [ ] `state.json` пишется атомарно, `chmod 600`, битый файл не ломает старт (лог + дефолт);
- [ ] токен нигде не пишется на диск и не попадает в `status`/лог (проверить тестом);
- [ ] `connect` не завершается без подтверждённого pairing-кода;
- [ ] `on/off` работает для сессии, воркспейса и глобально, приоритет как в 002;
- [ ] ошибки команд возвращают человеку текст, а не stacktrace;
- [ ] `node --test dsh-remote/test` — зелёный.

## Заметки

- Форма команд — `packages/interaction/commands/src/index.ts`: `handler`
  получает `invocation.agent`, `rawInput`, `signal`; имя команды — `[a-z][a-z0-9_-]*`.
- Локальный вопрос во время команды: `ctx.userQuestions.ask({questions, agent: invocation.agent, signal})`
  — это тот же путь, что у инструмента, и он не конфликтует с ответчиком из 002
  (режим ещё выключен).
- Секреты: `ctx.credentials` — `resolve(ref)`, `describe(ref)` (без значения,
  годится для UI), `set(ref, value)`, `unset(ref)`; резолв на каждую операцию
  (кэшировать нельзя — это механизм ротации без рестарта). Если сервиса нет —
  fallback на env и предупреждение в `status`. Подробности: `docs/research/dsh-hooks.md` §6.

- Концепция — `docs/CONCEPT.md` (разделы 3–8), спека — `.kanban/specs/001.md`.
- Каталог задачи — `worktrees/<id>` (ветка `task/<id>`). Сессия роли живёт в корне
  проекта, поэтому **работать только внутри `worktrees/<id>`**: `cd worktrees/<id>`,
  дальше всё относительно него; в корне и в чужих `worktrees/*` не писать.
- Общие файлы не трогать: `AGENTS.md`, `.kanban/` (кроме своей карточки), `bin/task-*.sh`.
- Профиль DSH (`~/.dsh/profiles`) в этой задаче не правится — установку делает человек/оркестратор.
- Язык: JS (ESM), только `node:` builtins; тесты — `node --test` (если `node` не в PATH — `bin/node.sh`).
- Все git-команды и `bin/task-move.sh` — из каталога задачи (`cd worktrees/005`);
  основную ветку и карточки других задач не трогать.
- Сдача: `cd worktrees/005 && bin/task-move.sh 005 in-review --role worker --tokens auto --note "..."`.
