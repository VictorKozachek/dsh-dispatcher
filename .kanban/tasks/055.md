## Задача

MAX Bot API принимает `text` **до 4000 символов**; наш транспорт для MAX режет по
`caps.maxText`, где стоит 4096 (значение по умолчанию из `base.js`). Вопрос,
чей HTML-текст попадает в диапазон 4001–4096, падает с

```json
{"code":"proto.payload","message":"Field 'text' size (4100) must be at most 4000"}
HTTP 400
```

и уходит в GUI (ответчик трактует ошибку как недоставку). Проверено вживую
2026-11-13 (`POST /messages` с `{"text": "x"*4100, "format":"html"}`).

## Требования

1. У MAX-транспорта `caps.maxText = 4000` (своя константа, не дефолт 4096);
   проверить, что `renderBody`/`renderHtml` и `clipEscaped` укладываются в этот
   лимит **с учётом HTML-разметки**, а не только видимого текста.
2. При приближении к лимиту — обрезка по границе строки/тега (как в 047) с
   маркером, а не «400 от сервера».
3. Ошибка `proto.payload` про размер должна попадать в журнал (`question.error`,
   после 051) и в `doctor`/`status` как понятная строка, а не «канал не поднят».
4. Тесты: текст 3999/4000/4001/4096 символов в MAX-транспорте — отправляется
   усечённый ≤4000, серверу не уходит 400; фейковый fetch проверяет фактическую
   длину `text` в теле запроса; Telegram-транспорт не задет (у него лимит 4096).

## Критерии готовности

- [ ] MAX-транспорт никогда не отправляет `text` длиннее 4000;
- [ ] длинный вопрос доставляется усечённым с понятным маркером;
- [ ] тесты на границы лимита для MAX (и регресс Telegram);
- [ ] `node --test` и `bin/ci.sh --fast` зелёные.
