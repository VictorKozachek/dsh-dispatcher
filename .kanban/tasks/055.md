## Задача

**Статус: гипотеза НЕ подтвердилась (проверено 2026-11-13).** В
`lib/transport/max.js` уже стоит `MAX_CAPS.maxText = 4000` (строка ~206), и
прямой прогон транспорта с вопросом на 5700 символов отправляет ровно **4000**
символов (`text.length === 4000`). То есть лимит MAX соблюдается, и «длинный
вопрос» сам по себе не является причиной падения.

Остаётся полезная часть — **закрепить это тестом** (регресс), потому что лимит
сервера реальный и легко ломается при правках рендера.

Историческая формулировка (оставлена для контекста): MAX Bot API принимает `text`
**до 4000 символов**; если транспорт начнёт отправлять больше (например, вернут
дефолт 4096 из `base.js`), вопрос упадёт с

```json
{"code":"proto.payload","message":"Field 'text' size (4100) must be at most 4000"}
HTTP 400
```

и уходит в GUI (ответчик трактует ошибку как недоставку). Проверено вживую
2026-11-13 (`POST /messages` с `{"text": "x"*4100, "format":"html"}`).

## Требования (сужены после проверки)

1. **Регресс-тест**: MAX-транспорт с вопросом на 5700 символов отправляет
   `text` длиной ровно ≤ 4000 (фейковый fetch проверяет фактическую длину),
   и разметка (`<pre>`) не рвётся при усечении.
2. Тест на границах: 3999 / 4000 / 4001 (вход) → в запросе всегда ≤ 4000.
3. Тест: Telegram-транспорт по-прежнему режет по 4096 (своя константа) — не
  耦合-регресс.
4. Если правки рендера понадобятся — только в рамках задачи, без изменения
   публичного поведения.

## Критерии готовности

- [ ] MAX-транспорт никогда не отправляет `text` длиннее 4000;
- [ ] длинный вопрос доставляется усечённым с понятным маркером;
- [ ] тесты на границы лимита для MAX (и регресс Telegram);
- [ ] `node --test` и `bin/ci.sh --fast` зелёные.
