# Совместимость протокола релея

Документ фиксирует правила эволюции [`PROTOCOL.md`](PROTOCOL.md) и
[`schema.json`](schema.json), чтобы плагин и релей обновлялись независимо.

## 1. Версия

- Версия протокола — в пути (`/v1/...`) и в заголовке `X-Relay-Version: 1`.
- `schema.json` содержит `"version": "1.0.0"`; минорная версия растёт при
  **аддитивных** изменениях, мажорная — при ломающих.
- Совместимость: релей поддерживает **все** минорные версии своей мажорной ветки;
  клиент обязан игнорировать незнакомые поля (аддитивность), но может требовать
  известный минимум.

## 2. Добавление полей — только аддитивно

Разрешено без смены мажорной версии:

- новое **необязательное** поле в существующей сущности;
- новое значение `error.code` (клиент обязан обработать незнакомый код как
  `internal` с `retryable: false`, а не падать);
- новый эндпоинт под `/v1/` (клиент, который его не знает, просто не зовёт);
- новое значение `type` у события (незнакомый тип игнорируется клиентом);
- новые `details` в ошибке (объект, клиент не разбирает неизвестные ключи).

Запрещено без `/v2`:

- удалить или переименовать поле/эндпоинт;
- сделать необязательное поле обязательным;
- сузить `enum`, `pattern`, `minLength`/`maxLength`, `minimum`/`maximum`;
- изменить смысл существующего поля;
- поменять формат `enc`/`nonce` (это ломает расшифровку на устройстве).

## 2a. Запросы строгие, ответы аддитивные

- **Запросы** (`DeviceCreateRequest`, `PairRequest`, `Question`, `QuestionPublishRequest`,
  `AnswerRequest`) — `additionalProperties: false`: лишнее поле даёт
  `400 bad-request`. Новое поле клиент отправляет только после того, как релей
  объявил его поддержку (см. §4).
- **Ответы** (`Device`, `PairResponse`, `QuestionList`, `Answer`, `Event`, `Health`,
  `Error`) — `additionalProperties: true`: незнакомые поля клиент **обязан**
  игнорировать. Поэтому `enum` у `error.code` и `event.type` заменён открытым
  шаблоном: релей может добавить код/тип в минорной версии, клиент не падает.

## 2b. Аддитивные дополнения, принятые в v1

Новые пути и необязательные параметры в рамках `/v1`; клиенты, которые их не
используют, работают как раньше:

- `POST /v1/pairing` — плагин получает одноразовый код привязки
  (`201` + `PairingCodeResponse`); в §3 документа 016 был только `POST /v1/pair`,
  принимающий код.
- `GET /healthz` — алиас `/v1/health` вне `/v1` (liveness/смок-пробы),
  та же схема `Health`.
- `?wait=<сек>` у `GET /v1/questions` и `GET /v1/answers` — long-poll fallback для
  устройства без WebSocket; по таймауту возвращается пустой ответ/`404`, не ошибка.
- `nextId` в `QuestionList` и необязательный `sinceId` в запросе — составной
  курсор пагинации (tie-break при одинаковом `createdAt`). Без `sinceId`
  поведение прежнее: `created_at > since`.
- Счётчики `devices`/`questions`/`answers` в `Health` — аддитивные поля.
- Необязательный `version` в теле запросов: допускается только `1`.

Повтор запроса с теми же `since`/`sinceId` идемпотентен: сервер возвращает то же
окно и тот же `nextId`.

## 3. Отзыв версии

- Мажорная версия живёт не меньше **90 дней** после публикации `/vN+1`.
- Отзыв объявляется заголовком `Sunset: <RFC 8594 дата>` в ответах `/vN` и
  ошибкой `410 expired` с `error.details.replacement = "/vN+1"` — не раньше чем
  за 30 дней до отключения.
- После отключения `/vN` отвечает `426 unsupported-version` с
  `error.details.supported: [1, 2]`.

## 4. Что делает плагин при несовпадении версий

1. **Ответ `426 unsupported-version`** — плагин не ретраит автоматически: пишет в
   журнал «релей требует версию X, плагин умеет Y», показывает человеку
   `/remote doctor` с этим текстом и **выключает доставку вопросов в релей**
   (fallback — мессенджер, если настроен). Это защищает от потери ответов.
2. **Заголовок `X-Relay-Version` в ответе больше ожидаемого минора** — плагин
   продолжает работать (аддитивность) и только логирует минорное расхождение.
3. **Заголовок меньше минимально поддерживаемого** — как `426`.
4. **Неизвестный `error.code`** — трактуется как `internal` (`retryable: false`),
   в журнал пишется код и `details`.
5. **Незнакомое поле в ответе** — игнорируется (схема протокола разрешает
   аддитивность на уровне клиента; `additionalProperties: false` действует только
   на запросы к релею).
6. **Несовпадение `keyId`/`alg` в конверте** — плагин не пытается расшифровать,
   помечает вопрос «нужен новый ключ» и просит человека перепривязать устройство.

## 5. Изменение схемы

- `schema.json` версионируется вместе с протоколом: любое изменение схемы
  сопровождается записью в этом файле (что добавлено/удалено и почему).
- Примеры в `examples/` обязаны валидироваться схемой; для каждого нового
  обязательного поля добавляется пример и негативный кейс.
- `docs/relay/validate.mjs` — эталонный валидатор подмножества JSON Schema,
  которым проверяются примеры; при расширении схемы новыми ключевыми словами
  валидатор расширяется в том же изменении.
