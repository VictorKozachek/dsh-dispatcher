# Концепция: удалённое управление вопросами агента (dsh-dispatcher)

Статус: черновик, версия 1 (ноябрь 2026).
Спека нарезки: [`.kanban/specs/001.md`](../.kanban/specs/001.md).
Справочные отчёты: [мессенджеры](research/messengers.md), [хуки DSH](research/dsh-hooks.md).

---

## 1. Проблема

Агент в DSH, дойдя до развилки, спрашивает человека инструментом
`ask_user_question` и **блокируется до ответа**. Если человек в этот момент не за
клавиатурой — работа стоит: сессия ждёт, задача не двигается, токены не тратятся,
но и прогресса нет. Чем длиннее автономный прогон (несколько задач, несколько
worktree), тем чаще агент упирается в такой вопрос — и тем дороже простой.

Что хочется:

1. Вопрос, заданный агентом, **приходит на телефон** — в мессенджер, который уже
   установлен (Telegram, MAX), без нового приложения.
2. В сообщении видно, **откуда** вопрос: воркспейс (проект), сессия, роль, а если
   сессия ведёт задачу с доски — её номер.
3. Ответ (кнопкой или текстом) **возвращается в ту же сессию** как ответ на
   вопрос, а не как новое сообщение пользователя: агент продолжает с того места,
   где встал.
4. Подключение — **командой в чате**: «подключить удалённое управление», выбор
   бота, ввод параметров, проверка — и дальше работает для всех сессий воркспейса.
5. Позже — свой сервис (Rust) и мобильные приложения, без переделки ядра.

Чего не хотим: держать ноутбук с белым IP, поднимать сервер, патчить ядро DSH,
превращать вопросы в чат «на память» и терять вопросы при перезапуске.

## 2. Что уже есть в DSH (и на чём это стоит)

Проверено по исходникам (`~/projects/deepseek-harness`, отчёт
[research/dsh-hooks.md](research/dsh-hooks.md)):

| Что нужно | Что есть | Где |
|---|---|---|
| Вопрос человека | инструмент `ask_user_question` → `ctx.userQuestions.ask({questions, agent, signal})` | `packages/interaction/tool-ask-user/src/index.ts` |
| **Точка перехвата** | waterfall-событие `user-questions/request` — композиция «ответчиков»; вернуть ответ или вызвать `next()` | `packages/interaction/user-questions/src/index.ts:136` |
| Форма вопроса | `{id, question, detail?, header?, options?: [{label, description?}], multiSelect?, intent?}` | `packages/interaction/user-questions/src/types.ts` |
| Форма ответа | `{answers: [{id, selected: string[], custom?: string}]}` | там же |
| Откуда вопрос | `request.agent.id` = `SessionId`; шапка сессии даёт `cwd` (воркспейс) и `agentPreset` (роль) | `packages/core/session/src/types.ts:68` |
| Команды в чате | `ctx.commands.register({name, description, handler})` — слэш-команды, исполняются без модели | `packages/interaction/commands/src/index.ts` |
| Секреты | `ctx.credentials` — конфиг хранит **ссылку** (имя env-переменной), значение живёт в keychain/`~/.dsh/.credentials.yaml` | `packages/credentials/*` |
| Пример host-плагина | `dsh-kanban`: `inject`, `ctx.on("agent-preset/selected")`, `sessionController.prompt` | `~/projects/dsh-kanban/dsh-kanban/lib/index.js` |
| Порядок ответчиков | `ctx.on(name, fn, { prepend: true })` — единственный способ встать **до** моста `api-remotes`, который отдаёт вопрос браузеру | `vendor/cordis/src/events.ts:288-296`, `docs/research/dsh-hooks.md` §2.2 |

Главный вывод: **ядро трогать не нужно**. Вопрос человека — это waterfall, в
который штатно встаёт ещё один ответчик. Именно так в него встаёт GUI
(`packages/client/ui-user-questions/src/client/index.ts:104`); ровно так же
встанет наш мост.

Смысл схемы: сообщение в мессенджере — не «ещё один чат», а представление
вопроса: у него есть id, дедлайн и привязка к сессии, а ответ возвращается ровно
туда, где агент встал.

## 3. Ключевое решение

Плагин **`dsh-remote`** (host-половина в профиле DSH) регистрирует ответчик
`user-questions/request`. Если для воркспейса включён удалённый режим, ответчик
**не отдаёт вопрос GUI**, а отправляет его в мессенджер и ждёт ответа; пришедший
ответ возвращается как `AskUserQuestionAnswer`. Сессия не знает, что человек
отвечал с телефона: для неё это обычный ответ на `ask_user_question`.

```
DSH host process
├─ agent (сессия, worktree задачи)
│   └─ ask_user_question ──┐
│                          ▼
│              waterfall 'user-questions/request'
│                          │
│              dsh-remote answerer ──(режим выключен)──▶ next() → GUI
│                          │ (режим включён)
│                          ▼
│                  RemoteQuestionBroker
│                  ├─ реестр вопросов, TTL, дедуп, очередь недоставленных
│                  ├─ состояние: ~/.dsh/remote-control/state.json
│                  └─ transport: telegram | max | fake(тесты)
│                          │ HTTP (long polling) — исходящее соединение
│                          ▼
└─ телефон: бот в Telegram/MAX ── кнопка или текст ──▶ ответ
                                                     │
                                    answerer возвращает ответ в сессию
```

Технические детали, без которых это не работает:

- **`prepend: true` обязателен.** Мост `api-remotes`, отдающий вопрос браузеру,
  регистрирует свой слушатель раньше любого плагина (ряд `api-remotes` монтируется
  до нашего). Без `prepend` наш ответчик окажется «внутри» цепочки и вызовется
  только если браузер вызвал `next()` — то есть уже никогда.
- **Забрали вопрос — `next()` не зовём.** Тогда remote-событие не создаётся, и в
  GUI ничего не «висит». Обратный сценарий (позвать `next()` и вернуть ответ
  быстрее браузера) опасен: кадр уже в очереди Gateway, снять его из плагина
  нельзя — панель останется висеть, а инструмент уже вернулся.
- **Таймаута на вопрос в DSH нет** (`ask_user_question` не объявляет
  `timeoutMs`), поэтому «человек не ответил N минут» — наша гонка с таймером.
- **Вопросы не персистятся** ядром: упал процесс — вопрос мёртв, ответ возвращать
  некуда. Это не лечится плагином, только честным «снято».

Почему так, а не «свой сервер»:

- **нет входящего трафика** — ноутбук за NAT сам ходит в Bot API (Telegram
  `getUpdates`), публичный адрес, домен и сертификат не нужны;
- **нет нового процесса** — плагин живёт в процессе DSH, где уже есть доступ к
  `userQuestions`, `commands`, `sessions`, `credentials`;
- **ответ приходит в ту же точку** — не «сообщение в чат», а результат
  инструмента: агент продолжает шаг, а не начинает новый турн;
- **смена канала ничего не ломает** — мессенджер спрятан за интерфейсом
  транспорта; будущий Rust-релей и мобильное приложение встанут на его место.

## 4. Компоненты

### 4.1. `dsh-remote` (host-плагин)

| Модуль | Ответственность |
|---|---|
| `answerer` | слушает `user-questions/request`; решает «удалённо или локально»; отдаёт `next()` при выключенном режиме; переводит вопрос в доменную модель и обратно |
| `broker` | реестр открытых вопросов, ожидание ответа (`Promise` + `AbortSignal`), TTL, идемпотентность, повторная доставка |
| `registry` | включён ли удалённый режим: глобально / для воркспейса (`cwd` сессии) / для сессии |
| `commands` | `/remote connect`, `on`, `off`, `status`, `test`, `pair`, `who` |
| `store` | `~/.dsh/remote-control/state.json` (атомарная запись), журнал без секретов; токены — через `ctx.credentials` |
| `transports/*` | `telegram`, `max`, `fake` — единый интерфейс, лимиты в `caps` |
| `present` | рендер сообщения: шапка «воркспейс · сессия · роль · задача», тело, варианты, дедлайн |

### 4.2. Клиентская половина (GUI)

Таб «Удалённое управление» в правом сайдбаре: статус (какой транспорт, какой
чат, какие воркспейсы включены), кнопка «тест», список открытых вопросов со
ссылкой на сессию, «снять вопрос», лог последних доставок (без секретов).
Не обязателен для MVP: всё то же делает `/remote status`.

Оговорка: исходники DSH в этом чекауте (`0.1.2-alpha.2`) **старше**
установленной сборки — в них нет ни `sidebarRightTabs`, ни слотов
`sidebar.right.*`, а клиентская половина `dsh-kanban` работает именно на них.
Поэтому GUI-часть пишем по образцу `dsh-kanban/lib/client.js` и проверяем в живом
профиле, а не по старому чекауту.

### 4.3. Модель вопроса (общая для всех транспортов)

```ts
interface RemoteQuestion {
  id: string;              // uuid вопроса
  shortId: string;         // 8 символов — в callback_data (<64 байт)
  transport: 'telegram' | 'max';
  chatId: string;
  messageId?: string;      // id сообщения в мессенджере
  sessionId: string;       // request.agent.id
  workspace: string;       // cwd сессии
  role?: string;           // agentPreset
  taskId?: string;         // номер карточки, если сессия ведёт задачу
  title?: string;          // header вопроса
  body: string;
  options: { id: string; label: string }[];
  multiSelect: boolean;
  allowFreeText: boolean;
  createdAt: number;
  expiresAt: number;
  status: 'pending' | 'open' | 'answered' | 'expired' | 'cancelled';
  answer?: { selected: string[]; custom?: string };
  answeredBy?: string;     // внешний user id
}
```

Правила домена:

- `pending → open` — сообщение доставлено; `→ answered` — ровно один раз
  (атомарный переход по статусу), повтор игнорируется и логируется;
- ответ принимается только от `userId` из allowlist **и** из привязанного чата;
- `cancel` приходит из DSH (`signal` абортится — человек нажал Esc или сессия
  закрыта): сообщение правится «вопрос снят», кнопки убираются;
- `expired` — по TTL; по умолчанию **агента не разблокирует** (см. §7.3).

### 4.4. Интерфейс транспорта

```ts
interface QuestionTransport {
  readonly id: 'telegram' | 'max' | 'fake';
  readonly caps: { inlineButtons: boolean; editAfterAnswer: boolean; maxText: number; };
  start(): Promise<void>;                       // поднимает long polling
  stop(): Promise<void>;
  sendQuestion(q: RemoteQuestion, to: { chatId: string }): Promise<{ messageId: string }>;
  closeQuestion(q: RemoteQuestion, summary: string): Promise<void>;
  onAnswer(handler: (a: IncomingAnswer) => Promise<void>): void;
  healthCheck(): Promise<{ ok: boolean; detail?: string }>;
}
```

Правила, которые делают второй транспорт дешёвым: наружу не отдаём `message_id`
и разметку; лимиты — в `caps`; дедупликацию апдейтов и курсор (`offset`/`marker`)
держит транспорт; `callback_data` — `q:<shortId>:<opt>`; прикладной код не знает
про платформы.

## 5. Сценарий использования

### 5.1. Подключение (команда в чате)

```
Вы:  /remote connect
DSH: (локальный вопрос — удалённый режим ещё не включён)
     Какой мессенджер?        [Telegram] [MAX]
     Вставьте токен бота:     [____]
     Напишите боту /start и отправьте ему код 481-572
     ✅ Привязано: @my_agent_bot · chat 123456789 · user 987654321
     Подключить для: [этого проекта] [всех проектов]
     Удалённое управление включено: dsh-dispatcher
```

- выбор мессенджера и ввод токена идут через **обычный локальный** вопрос —
  удалённый канал ещё не поднят, поэтому спрашивать некого;
- токен сохраняется как ссылка (`DSH_REMOTE_TELEGRAM_TOKEN` в keychain/env), в
  конфиг и логи не попадает;
- pairing-код одноразовый, TTL 10 минут: пока человек не прислал его боту,
  бот не принимает чужих сообщений (`allowlist` пуст);
- `/remote status` показывает, что привязано и для каких воркспейсов включено.

Дальнейшие команды: `/remote on` (этот воркспейс), `/remote off`,
`/remote on --all` (все воркспейсы на этой машине), `/remote test` (прислать
тестовый вопрос в чат), `/remote who` (привязка и allowlist), `/remote doctor`
(проверка: токен, поллинг, задержка, лимиты).

### 5.2. Вопрос уходит в телефон

```
▸ dsh-dispatcher · task 007 · worker · 17:41 · до 18:11

Удалить ветку task/007 после слияния?

[ Да, удалить ]  [ Оставить ]
[ Другой ответ… ]
```

- первая строка — «откуда»: воркспейс, задача, роль, время, дедлайн;
- варианты — инлайн-кнопки (одна на строку, максимум 8; больше — «Показать
  ещё»), `multiSelect` — кнопки-тумблеры + «Готово»;
- «Другой ответ…» переключает в режим свободного текста: следующий текст/reply
  от человека считается ответом на этот вопрос;
- после ответа сообщение правится: `✅ Да, удалить · 17:42`, кнопки снимаются;
- вопрос без вариантов — просто текст, ответ ждём reply или любым сообщением,
  если открыт ровно один свободный вопрос.

### 5.3. Несколько сессий и вопросов одновременно

Один чат — один поток, поэтому:

- каждый вопрос самоидентифицируем: маркировка в тексте + `shortId` в
  `callback_data` (нажатие кнопки не требует разбора текста);
- свободный ввод привязывается reply-to к сообщению вопроса, поэтому ответ не
  путается между сессиями;
- если открыто несколько свободных вопросов и пришёл текст без reply — бот
  отвечает «уточните, к какому вопросу» и показывает список;
- вопросы нумеруются по порядку, в шапке виден дедлайн;
- отдельный бот/чат на проект — опционально (фаза 2), по умолчанию один бот на
  все проекты машины.

## 6. Где что живёт

| Данные | Место | Примечание |
|---|---|---|
| Состояние (вопросы, привязки, курсоры, включённые воркспейсы) | `~/.dsh/remote-control/state.json` | атомарная запись, `chmod 600`, вне репозитория |
| Секреты (токены) | `~/.dsh/.credentials.yaml` через `ctx.credentials` (`resolve`/`describe`/`set`, ссылка — POSIX-имя вроде `DSH_REMOTE_TELEGRAM_TOKEN`; окружение главнее файла) | конфиг хранит только имя ссылки |
| Конфиг плагина | ряд `dsh-remote` в `cordis.patch.yml` профиля | `boards`-подобный список воркспейсов не нужен: включение живёт в state |
| Журнал доставок | `~/.dsh/remote-control/log.jsonl` | без токенов, без тел вопросов (по умолчанию) |
| Карточки задач | `.kanban/tasks/*.md` | только чтение: номер задачи для шапки |

Проекты друг друга не трогают: плагин глобальный, но состояние — на машину, а
включение — на воркспейс. Доска задач проекта (`dsh-kanban`) остаётся
собственностью проекта; наша интеграция с ней — read-only.

## 7. Поведение в неудобных случаях

### 7.1. Человек ответил в GUI, а не в телефоне

В режиме `remote-only` вопрос в GUI не показывается вовсе, поэтому гонки нет.

Режим `mirror` («видно и там, и там») технически невозможен в наивном виде:
вопрос, уже отданный браузеру, из плагина не снять (снятие — только аборт
`signal` запроса, то есть аборт самого tool-call). Поэтому честный гибрид другой —
**`hybrid`**: отправляем в мессенджер, ждём `N` секунд (по умолчанию 20); не
ответили — **до** всякой публикации зовём `next()` и вопрос уходит в GUI; если
телефон ответит позже, ответ доставляется в сессию сообщением
(`sessionController.prompt`, режим `steer`), а не как результат инструмента.
Это осознанная деградация, зато без висящих панелей. В MVP режима нет.

### 7.2. Мессенджер недоступен / 429 / нет сети

Вопрос помечается `pending`, лежит в очереди, повтор с экспоненциальной паузой
(учитываем `retry_after` у Telegram). Если за `connectTimeoutMs` (по умолчанию
30 с) доставить не удалось — ответчик отдаёт вопрос `next()`, то есть **в GUI**:
лучше спросить локально, чем молчать. В журнал — причина.

### 7.3. Человек не ответил

- за 5 минут до TTL — мягкое напоминание **правкой** сообщения («⏳ осталось 5
  минут»), без нового уведомления;
- по TTL — `expired`: кнопки снимаются, сообщение помечается «⌛ ждёт ответа»,
  повторный пуш не чаще раза в 30 минут;
- **агента не разблокируем угаданным ответом.** Но и держать вечно нельзя
  (таймаута в DSH нет), поэтому у истечения три явных исхода и один из них
  обязателен в конфиге: `onExpire: 'abort'` (по умолчанию — вернуть ошибку
  `ASK_ABORTED`, модель видит, что вопрос не отвечен, и продолжает по своему
  умолчанию), `'empty'` (вернуть `selected: []` + `custom: "(нет ответа)"`) или
  `'default-first'` (первый вариант — он и рекомендованный по контракту
  `ask_user_question`).
- поздний ответ принимается с флагом `late`: если вопрос ещё открыт — применяется,
  если снят — уходит в сессию сообщением (`steer`) или, когда сессии уже нет,
  отбрасывается с уведомлением «вопрос уже закрыт».

### 7.4. DSH перезапустили с открытыми вопросами

Ядро вопросы не персистит («Session control neither stores nor replays these
requests»): если процесс умер, ответ уже некуда вернуть. Поэтому при старте
плагин читает state, помечает «осиротевшие» вопросы
`cancelled`, правит сообщения («сессия перезапущена, вопрос снят») и не пытается
их оживить. Сессия после resume, дойдя до вопроса заново, задаст его снова — уже
с новым `id`.

### 7.5. Вопрос содержит секреты

Тело вопроса уходит на серверы мессенджера. По умолчанию включаем «вычищалку»:
маскирование известных форматов (токены `bot\d+:…`, ключи `sk-…`, приватные
ключи, длинные base64-подобные строки) и предупреждение в шапке, если что-то
замаскировано. Полный запрет — `redact: 'strict'` (тело не отправляется, только
«вопрос скрыт, ответьте в GUI»).

## 8. Безопасность

- **Allowlist по user id**, не по чату: Telegram — `from.id` / `callback_query.from.id`,
  MAX — `update.user.user_id`. Плюс проверка `chatId`. Всё прочее игнорируется и
  логируется.
- **Pairing** одноразовым кодом (TTL 10 мин) — бот не принимает ответов, пока
  привязка не подтверждена; `/remote who` показывает, кто привязан.
- **Токен** — только через `ctx.credentials` (keychain/`~/.dsh/.credentials.yaml`),
  в конфиге — имя ссылки, в логах — маска, в state — никогда.
- **Один поллер на токен**: Telegram отвечает `409 Conflict` при двух
  `getUpdates`; берём лок-файл в `~/.dsh/remote-control/`.
- **Идемпотентность**: `offset = update_id + 1` после обработки; ответ применяется
  один раз (переход статуса); повторные нажатия кнопок игнорируются.
- **Границы доверия**: плагин работает в процессе DSH с правами человека —
  никакого нового сетевого входа не появляется, только исходящий трафик к Bot API.
- **Отзыв**: `/remote disconnect` снимает токен и allowlist; смена токена у
  @BotFather инвалидирует старый.

## 9. Транспорты: что первым и почему

Полная справка — [research/messengers.md](research/messengers.md).

| | Telegram | MAX |
|---|---|---|
| Бот заводится | за минуту, физлицом | только юрлицо/ИП/самозанятый РФ, модерация до 48 ч |
| За NAT без белого IP | **да** — `getUpdates` (long polling) | формально `GET /updates`, но документация называет его не-production; webhook — только 443 + доверенный CA |
| Кнопки + колбэки | да | да |
| Лимиты | 4096 симв., ~1 msg/с в чат, 429 + `retry_after` | 4000 симв., 2 msg/с в чат, `retry_after` не документирован |
| Доступность в РФ | риск (ограничения с 2026) | национальный мессенджер |

**Решение: первым Telegram** (нулевая инфраструктура, работает с ноутбука за
NAT, документированные лимиты), **вторым MAX** — как второй канал для
устойчивости: один и тот же вопрос уходит в оба, ответ принимается первый,
второй канал помечается «отвечено в другом». Транспорт выбирается в
`/remote connect`, переключение — без переустановки.

Отдельно рассматривали как «дешёвый канал» ntfy/Apprise — годится для
уведомлений, но интерактивные ответы (кнопки + колбэки + правка сообщения) там
беднее; держим в уме как третий `caps`-транспорт на будущее.

## 10. MVP и фазы

### MVP (спека 001)

1. Плагин `dsh-remote` в профиле, конфиг-схема, состояние на диске.
2. Ответчик `user-questions/request` + реестр вопросов + TTL + отмена.
3. Транспорт `telegram` (long polling, кнопки, свободный текст, правка).
4. Команды `/remote connect|on|off|status|test|who|disconnect`.
5. Маркировка «воркспейс · задача · роль», allowlist, pairing, секреты.
6. `fake`-транспорт и тесты без сети; документация и установочный скрипт.

### Фаза 2

- транспорт MAX (два канала одновременно, «первый ответ побеждает»);
- режим `mirror` (вопрос и в GUI, и в телефоне);
- уведомления о событиях доски (задача ушла в `ready`, тесты упали) — в тот же
  канал, но **без** подмены карточки: доска остаётся источником истины;
- группировка по проектам (Telegram-топики или отдельный чат на проект);
- `/remote pair` для второго устройства, журнал и метрики задержек.

### Фаза 3 (спека 002)

Свой сервис на Rust + приложения Android/iOS:

- релей с WebSocket/HTTP2, push (APNs/FCM) и оффлайн-очередью;
- e2e-шифрование тела вопроса (ключ на устройстве), сервер видит только конверт;
- плагин остаётся тем же: он реализует `QuestionTransport`, который ходит на
  релей вместо Bot API — код ответчика и домена не меняется;
- несколько устройств, «прочитано», история вопросов, поиск.

Почему не начинать с приложения: без публичного адреса всё равно нужен релей,
а релей — это инфраструктура, деплой и оплата. Мессенджер даёт тот же эффект
сегодня и проверяет сам сценарий; приложение — следующий шаг, когда станет ясно,
каких кнопок и уведомлений не хватает.

## 11. Альтернативы и почему отказались

| Вариант | Почему нет (сейчас) |
|---|---|
| Webhook-сервер на VPS + бот | нужна инфраструктура, сертификат, публичный адрес; для одного человека — избыточно |
| Локальный HTTP-сервер + браузер телефона (Tailscale/порт) | работает, но требует VPN/проброса и «своего» UI; мессенджер уже стоит в кармане |
| Email/SMS-шлюз | медленно, дорого, нет кнопок |
| Полностью внешний сервис (SaaS-бот) | тела вопросов уходят третьей стороне, привязка к сессиям — своя |
| Править ядро DSH | не нужно: waterfall `user-questions/request` — штатная точка расширения |
| Отвечать «сообщением в сессию» (`sessionController.prompt`) вместо ответа инструмента | агент не разблокируется: он ждёт результат `ask_user_question`, а не новый турн |

## 12. Риски и открытые вопросы

**Риски**

1. **Порядок waterfall.** Наш ответчик и GUI-ответчик живут в одном waterfall;
   если GUI зарегистрируется раньше и «заберёт» вопрос, удалённый режим не
   сработает. Проверить экспериментом до реализации (задача 002).
2. **Потеря вопроса при падении DSH** — лечится только «снятием» сообщения и
   повторным вопросом после resume; обещать доставку нельзя.
3. **Telegram недоступен из РФ** — второй канал MAX, переключение в `/remote`.
4. **Утечка тела вопроса** в мессенджер — redact + предупреждение.
5. **Два процесса/профиля с одним токеном** — `409 Conflict`; лок-файл и явная
   ошибка в `/remote doctor`.
6. **Соблазн «удалённо всё»** — удалённый режим не отменяет человека в GUI:
   `mirror` появится, когда будет проверен; до этого режим явный и видимый.

**Открытые вопросы к человеку**

1. Telegram первым — подтверждаем? (MAX требует ИП/юрлица и модерации.)
2. Нужен ли `mirror` (вопрос и в GUI, и в телефоне) в MVP или достаточно
   `remote-only`?
3. TTL вопроса: 30 минут по умолчанию — нормально? Что делать по истечении:
   эскалировать (по умолчанию) или отвечать первым вариантом?
4. Один бот на все проекты или по боту на проект?
5. Где хранить токен: keychain macOS (по умолчанию) или `.env` в `~/.dsh`?
6. Нужны ли в тот же канал уведомления доски (задача в `ready`, тесты упали) —
   или только вопросы?
