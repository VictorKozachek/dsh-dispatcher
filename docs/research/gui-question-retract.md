# Можно ли из плагина погасить вопрос в GUI (аудит, 058)

Версия хоста: **0.2.1-rc.5** (`/Applications/DeepSeek Harness.app/Contents/Resources/app.asar`,
распакован в `/tmp/dsh-host` при аудите). Проверялись `@deepseek-ai/dsh-user-questions`,
`dsh-tool-ask-user`, `dsh-api-remotes`, `dsh-client-ui-user-questions`,
`dsh-client-ui-chat` и `dsh-api-session-controller`.

Короткий ответ: **A (полный mirror) сейчас невозможен без правки хоста**. Плагин не
может ни снять уже отрисованную карточку, ни вернуть ответ за неё после `next()`.
Реализуем **B (полу-зеркало: GUI — источник истины, мессенджер — уведомление)**.
Вариант C — текущий режим «только мессенджер», без карточки GUI.

---

## 1. `UserQuestionService` — публичный интерфейс

`@deepseek-ai/dsh-user-questions/lib/index.js`:

| Метод | Строки | Что делает | Можно ли погасить GUI |
|---|---|---|---|
| `ask(request)` | 668–686 | разворачивает waterfall `user-questions/request`, ждёт ответа | нет: сам ничего не снимает, возвращает только ответ/ошибку |
| `askTimed(request, callId, timeoutMs)` | 613–661 | timed-вариант: по таймауту возвращает `{pending:true, callId}`, вопрос остаётся answerable | нет; после таймаута вопрос становится `continued`, но снять его нельзя |
| `attachWait(agent, callId, signal)` | 596–600 | stream для UI: отдаёт оставшееся время, держит claim | нет; закрытие stream только освобождает claim |
| `answer(agent, callId, answer)` | 552–594 | **только для `continued`** timed-вопроса: стеерит ответ в агента | не для открытого вопроса: `continued(agent).find(...)` вернёт пусто → `false` |
| `continued(agent)` | 536–540 | список `continued` из проекции `userQuestions` | только чтение |

Нет `cancel`, `settle`, `list`, `pending`, `dismiss`. Внутренние `waits` (Map
открытых foreground-ожиданий, строка 452+) и `queuedReplies` приватны; снаружи к
ним доступа нет. `@Remote` навешан только на `answer` и `attachWait` (строки
455–456) — это Client-facing RPC, не Host API.

**Вывод:** из host-плагина нет метода, который снял бы открытую карточку.
`answer()` для живого (не continued) вопроса — no-op/`false`, а не закрытие.

## 2. Мост GUI: что уходит в браузер и что приходит обратно

`@deepseek-ai/dsh-api-remotes/lib/index.js` (allowlist forwarded events, строки
120–140): из событий вопросов в браузер форвардится **только**
`user-questions/request` в режиме `waterfall` (строки 136–139). Событий
`user-questions/answered`, `.../resolved`, `.../cancelled` в allowlist нет, как и
`cancelRemoteEvent`. То есть:

- вопрос приходит в браузер как forwarded waterfall;
- ответ браузера — это **возвращаемое значение** этого waterfall, а не отдельный
  RPC-канал;
- плагин не получает уведомление «в GUI ответили» через Remote Events.

Карточка в браузере (`@deepseek-ai/dsh-client-ui-user-questions/lib/client.js`):

- карточка создаётся по forwarded-запросу и/или строке проекции, ключ —
  `sessionId + callId` (строки 1640–1660);
- карточка **удаляется только когда проекция `userQuestions` больше не содержит
  call и у карточки нет живого запроса/waterfall** (строки 1879–1882);
- закрытие панели (`dismiss`) для tool-call-keyed карточки — это `hide`, а не
  отмена: запрос остаётся живым, карточка возвращается из строки tool-call
  (строки 408–421). Отмена (`ASK_CANCELLED`) — только для безымянного legacy
  запроса без callId;
- `detachWaterfall` (строки 273–300) снимает канал, но карточку не удаляет.

Важно: проекция `userQuestions` ведёт **только timed-вопросы**. В
`applyUserQuestionEvent` `tool/call` игнорируется, если `fold.timed` ложно
(строки 199–201): legacy (blocking) `ask_user_question` в проекцию не попадает.
Значит для обычного blocking-вопроса нет и проекционной строки, по которой
карточка могла бы быть убрана; её судьба завязана на завершение forwarded
waterfall.

**Вывод:** «погасить» карточку можно только так, чтобы запрос, который её
породил, завершился (waterfall вернул результат/ошибку) — либо правкой хоста.
Отдельного «снимите карточку» канала нет.

## 3. Waterfall `user-questions/request` и `next()`

`@deepseek-ai/cordis/lib/index.js`, `waterfall` (строки 317–325):

```js
waterfall(...args) {
  const cbs = this.dispatch("waterfall", args);
  const inner = args.pop();
  const next = () => (cbs.shift() ?? inner)(...args);
  args.push(next);
  return next();
}
```

Слушатель может:

1. вернуть ответ, не вызывая `next()` — он владеет вопросом;
2. вызвать `next()` и получить ответ следующего слушателя (моста GUI) — тогда он
   **может вернуть другое значение**, и именно оно станет результатом
   `ask_user_question` (проверено harness'ом, ниже);
3. вернуть ответ, **не дожидаясь** `next()` — тогда downstream-запрос остаётся
   висеть: у плагина нет ссылки, чтобы его отменить/завершить.

Эксперимент на распакованном `@deepseek-ai/cordis` (не мок, реальный waterfall):

```
plugin:before-next | gui:got-request | gui:answered | plugin:after-next:{"answers":[{"id":"q1","selected":["from-gui"]}]}
RESULT {"answers":[{"id":"q1","selected":["from-messenger"]}]}
```

То есть плагин может дождаться ответа GUI и вернуть вместо него ответ
мессенджера. Но это **не mirror**: GUI-ответ уже получен и карточка закрывается,
а инструмент получает другой ответ — пользователь в GUI видит один результат,
модель — другой. Для 059 это недопустимо.

Эксперимент с гонкой (вернуть ответ мессенджера, не дожидаясь GUI):

```
plugin:call-next | gui:got-request | plugin:winner:{"answers":[{"id":"q1","selected":["from-messenger"]}]}
```

Downstream GUI-запрос остался pending; `next()`-промис никто не завершил, и
отменить его из плагина нечем. Карточка в браузере при этом остаётся живой
(у неё есть `hasRequest()`/`hasWaterfall()`), пока не придёт проекционное
событие — для legacy-вопроса его не будет. Это утечка и «зависшая плашка», а не
полный mirror.

## 4. Аборт: что видит GUI и сессия

- `ask()` проверяет `request.signal?.aborted` и бросает `ASK_ABORTED`
  (строки 668–670, 680–686). Аборт **запроса** завершает waterfall ошибкой.
- В браузере forwarded request получает `signal`; `createWaterfallRequest`
  подписывается на `abort` и реджектит канал `ASK_ABORTED`
  (`client.js:83–112`). Карточка при этом не удаляется: удаление — только по
  проекции (см. §2).
- Абортировать **только представление**, не трогая tool-call, нельзя: единственный
  signal — это signal запроса, который принадлежит вызову инструмента. Плагин
  его не создаёт и не может заменить; `sessionController.cancel()` отменяет
  **весь turn** агента (`dsh-api-session-controller/lib/index.js:3249–3254`), а не
  карточку вопроса.

**Вывод:** аборт — это «отменить вопрос вместе с tool-call», а не «убрать
карточку, оставив вопрос». Для mirror не годится.

## 5. События, которые плагин может слушать

- **Forwarded Remote Events:** только `user-questions/request` (см. §2).
  Событий answered/cancelled в allowlist нет; добавить их — правка
  `dsh-api-remotes/src/remote-events.ts` (один entry) и контракта события.
- **Host-side `session/event`:** плагин может подписаться на глобальное
  `ctx.on("session/event", ...)` (так делает сам `UserQuestionService`, строки
  515–520). В событиях есть `tool/call`, `tool/result`, `user/message`:
  по `tool/result` с `name === "ask_user_question"` можно увидеть ответ GUI
  (content — JSON `{answers}`), по `user/message` с
  `source.kind === "user-question-reply"` — поздний ответ на `continued` вопрос.
  Это **чтение**, а не управление: плагин узнаёт, что GUI ответил, но не может
  вернуть ответ за GUI.
- `agent-preset/selected` и прочие каналы к вопросам отношения не имеют.

## 6. Варианты для 059

### A. Полный mirror (гасим GUI из плагина)

**Сейчас не реализуем.** Нужна правка хоста, минимум один из швов:

1. Публичный метод `UserQuestionService.cancel(agent, callId, reason)` /
   `settle(agent, callId, answer)` для **живого** запроса + Remote-метод для
   клиента; плагин получает callId из `request.wait.callId` (legacy и timed
   передают его в `wait`, см. `dsh-tool-ask-user/lib/index.js:186–198`).
2. Либо вернуть из `ask()`/`askTimed()` handle с `settle/cancel`, который
   переживает `next()`; либо отдельный `user-questions/resolved` forwarded event
   и право завершать waterfall после `next()`.

Гарантии после правки: карточка снимается по `callId`; ответ из мессенджера
может завершить tool-call; нужна защита от гонки «оба ответили» (first-wins,
late-answer → steer/audit, как в 013). Риски: два источника истины, отмена
чужого tool-call, потеря ответа GUI, auth/скоуп агента.

**Не делать в 059 без отдельной карточки на хост.**

### B. Полу-зеркало (рекомендуется)

GUI — источник истины; плагин **не забирает** вопрос, а вызывает `next()`, чтобы
карточка появилась, и параллельно публикует копию в мессенджер:

- `const gui = await next();` — получает ответ GUI;
- до/во время ожидания отправляет вопрос в мессенджер с пометкой «ответьте в
  GUI»; ответ из мессенджера **не** принимается как ответ инструмента, можно
  ответить подсказкой/закрыть;
- когда `gui` разрешился (или `next()` бросил `ASK_ABORTED`), плагин возвращает
  ровно `gui` (не подменяет!), закрывает/редактирует сообщение в мессенджере
  («ответ дан в GUI: …»);
- если нужен лейт-ответ из мессенджера, его можно отправить в сессию как steer
  (`sessionController.prompt`) — это будет сообщение, а не результат tool-call;
  помечать как «уточнение», не как ответ.

Что нужно: изменение `answerer` (режим mirror), отправка/закрытие сообщения
после `next()`, тесты на «GUI ответил → мессенджер закрыт», «мессенджер ответил
раньше → подсказка, GUI не тронут», «abort → сообщение закрыто». Гарантий
полного mirror нет: ответ из мессенджера не меняет tool-result; карточка GUI
живёт до ответа/аборта; при закрытии браузера вопрос остаётся.

### C. Best-effort (текущий режим)

Плагин забирает вопрос (не зовёт `next()`), отвечает через мессенджер; GUI
карточку не показывает. Либо наоборот — GUI владеет, мессенджер только
уведомляет. Никаких гарантий синхронности; для 059 это запасной вариант, если B
окажется слишком дорогим.

## 7. Что брать в 059

Рекомендация: **B**, узкий срез:

1. Новый режим `mirror` в answerer (по конфигу), который вызывает `next()` и
   получает ответ GUI; возвращает **только** его.
2. Публикация копии вопроса в мессенджер с явной пометкой «ответ в GUI»;
   ответ из мессенджера не считается ответом инструмента (подсказка/закрытие).
3. После `next()` — закрыть/отредактировать сообщение с результатом GUI
   (без текста ответа, если он секретный: «ответ дан в GUI»).
4. Тесты: ответ GUI → сообщение закрыто; ответ мессенджера до GUI → подсказка,
   tool-call не завершён; abort → сообщение закрыто; fallback без GUI — текущий
   режим.
5. Отдельно (если нужен A) — карточка на хост: `UserQuestionService` cancel/
   settle для живого запроса + forwarded event; без неё A не начинать.

## 8. Ограничения аудита

Живой GUI-клиент в этом аудите не подключался: профиль DSH общий и правка
`~/.dsh/profiles` вне рабочей директории задачи запрещена. Проверено:

- код хоста 0.2.1-rc.5 (распакованный `app.asar`) — методы/события/строки выше;
- реальный `@deepseek-ai/cordis` waterfall — два harness-эксперимента (§3):
  `next()` + override и early-return с зависшим downstream;
- код клиентской карточки — условие удаления и поведение `dismiss` (§2).

Для приёмки B нужен один ручной прогон с живой карточкой GUI (ответ в GUI →
сообщение в мессенджере закрывается; ответ в мессенджере → подсказка).
