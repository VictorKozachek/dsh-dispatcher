# RUNBOOK эксплуатации `dsh-remote`

Что делать, когда удалённое управление вопросами работает не так, как ждёшь.
Рассчитан на человека, который ставил плагин по `docs/user-guide.md` и дежурит
по нему. Все команды — из DSH или шелла; секреты в выводе не появляются.

## Как быстро понять, что сломалось

```bash
# В DSH:
/remote status          # режим, привязка, очередь, подтверждения, политика
/remote doctor          # health-модель ok/warn/fail с подсказками
/remote doctor --json   # то же машинно (для скриптов и мониторинга)
/remote stats           # счётчики и латентность с момента старта плагина
/remote audit 20        # последние решения по подтверждениям
```

`/remote doctor` — главная точка входа: у каждой `fail`-проверки есть `action`
(«что делать»), и ниже для каждого такого кода есть раздел. Коды:
`token`, `getme`, `credentials`, `relay`, `schema`, `timers`, `state`
(остальные — `plugin`, `lock`, `channel`, `permissions` — только `warn`).

`/remote stats --json` отдаёт фиксированную структуру: `questions`, `approvals`,
`deliveries`, `errors`, `queues`, `latency` (бакеты), `uptimeMs`. Тела вопросов и
токены в метрики не попадают.

## SLO: что считаем «живым»

| SLO | Цель | Как мерить |
|---|---|---|
| Ответ доставляется быстро | **p95 ≤ 2 с** от вопроса до ответа человека (штатный Telegram, без ретраев) | `/remote stats --json` → `latency.buckets`: сумма `count` бакетов до `le: 2000` / `latency.count` ≥ 0.95 |
| Ни один вопрос не теряется при рестарте | после падения/перезапуска профиля `pending` не растёт, «осиротевшие» вопросы сняты | `/remote status` (строка подтверждений/очереди) + `/remote doctor` (`timers`, `schema`); в журнале `~/.dsh/remote-control/log.jsonl` — записи `orphan-cancelled` без повторных `orphan-failed` |
| Доставка не деградирует | `deliveries.failed` = 0 и `deliveries.retried` = 0 на здоровом канале | `/remote stats --json` → `deliveries`; рост `errors.telegram/relay` — повод смотреть канал |
| Очередь и таймеры не копятся | `queues.deliveries_pending = 0`, `queues.timers_active` ≤ числа открытых вопросов, `pending` ≤ `maxPending` (200) | `/remote stats --json` → `queues`; `/remote doctor` → `timers` |
| Плагин не течёт по времени | `uptimeMs` растёт, а `state.json`/журналы ограничены ротацией | размеры файлов в `~/.dsh/remote-control/`; `/remote doctor` → `state`, `schema` |

SLO — ориентиры для дежурного, а не жёсткий SLA: латентность зависит от сети
Telegram/MAX/релея. Если p95 > 2 с стабильно — смотрите `errors` и `relay`.

## Инциденты

Каждый раздел: **симптомы → быстрая проверка → действие → профилактика**.

### Бот молчит (вопросы не приходят в чат)

<!-- doctor-fail: token -->

**Симптомы.** `/remote status` показывает «режим выключен» или «транспорт не
поднят»; в чате нет сообщений; DSH-сессия ждёт ответа до TTL.

**Быстрая проверка.** `/remote doctor` → `token` (ссылка на секрет, источник,
`writable`) и `getme` (бот отвечает?), `channel` (последняя ошибка поллера).

**Действие.**

1. Если `token` = fail: задайте секрет `DSH_REMOTE_TELEGRAM_TOKEN` (или
   выполните `/remote connect`) — источник секретов указан в `detail`.
2. Если `getme` = fail: проверьте сеть до `api.telegram.org`; токен мог быть
   перевыпущен.
3. Если `channel` = warn с последней ошибкой: поллинг повторяется сам с backoff;
   при 401/403 — токен недействителен (см. «Токен отозван»).
4. Убедитесь, что режим включён: `/remote on` (`/remote on --all` для всех
   воркспейсов); выключенный режим — штатное поведение, вопросы идут в GUI.

**Профилактика.** Секрет — только через `ctx.credentials`; `bin/install-remote.sh`
проверяет установку; `/remote doctor` в мониторинге раз в N минут.

### Токен отозван или недействителен

<!-- doctor-fail: getme -->

**Симптомы.** В логе `Telegram: 401 Unauthorized`; `/remote doctor` → `getme` =
fail; вопросы не уходят.

**Быстрая проверка.** `/remote doctor` (`getme`, `token`); `@BotFather` → `/mybots`
→ бот → «API Token».

**Действие.** Перевыпустите токен у `@BotFather` (`/revoke`), положите его в
секрет `DSH_REMOTE_TELEGRAM_TOKEN` (или `/remote connect` заново). Старый токен
после `/revoke` недействителен сразу — второй поллер не поможет.

**Профилактика.** Не храните токен в git/профиле; после смены секрета
перезапустите профиль; мониторьте `getme`.

### 409 Conflict: два поллера одного бота

**Симптомы.** Вопросы приходят через раз, в логе `409 Conflict`; `/remote doctor`
→ `lock` = warn «lock держит pid …»; `/remote status` — канал с ошибкой.

**Быстрая проверка.** `/remote doctor` (`lock` — pid владельца); `ps -p <pid>`;
второй процесс — старая копия DSH, ручной `dsh web` или зависший `connect`.

**Действие.** Остановите лишний процесс (не kill -9, если можно): один бот — один
поллер. Если lock устарел (процесса нет) — перезапустите профиль: lock
перехватится. `/remote disconnect` освобождает привязку и останавливает поллер.

**Профилактика.** Не запускайте две копии DSH с одним профилем/токеном;
`/remote doctor` покажет конфликт до того, как вопросы начнут теряться.

### Диск заполнен или состояние не пишется

<!-- doctor-fail: state -->

**Симптомы.** Изменения режима «не сохраняются», `/remote status` показывает
старое; в логе ошибки записи `state.json`; `/remote doctor` → `state` = fail
(«не прочитан») или `permissions` = warn (права не 600).

**Быстрая проверка.**

```bash
df -h ~/.dsh/remote-control
du -sh ~/.dsh/remote-control/*
/remote doctor            # state, permissions, schema
/remote doctor --json     # машинно
```

**Действие.** Освободите место: `dsh-remote` ротирует журналы сам (аудит —
256 КиБ × 3, лог — 512 КиБ × 5), плюс есть принудительная очистка:
`/remote vacuum --dry-run` (показать, что удалится) → `/remote vacuum`. Старые
`state.json.bak-*` и чужие файлы тоже могут занимать место — удалите лишние
бэкапы (свежий оставьте). Права: `chmod 600 state.json`. Запись атомарная
(tmp → rename), поэтому «полуфайла» не бывает.

**Профилактика.** Мониторьте свободное место; `state.json.bak-*` от миграций
удаляйте после проверки; не держите в `~/.dsh/remote-control` посторонние файлы.

### Битый `state.json` или файл из будущего

<!-- doctor-fail: schema -->

**Симптомы.** `/remote status` — всё выключено, будто плагин только поставили; в
логе «состояние: битый JSON» или «state.json версии N новее плагина»; `/remote
doctor` → `state`/`schema` = fail.

**Быстрая проверка.** `/remote doctor` → `schema` (версия и инструкция);
`ls -la ~/.dsh/remote-control/state.json*`; `python3 -m json.tool < state.json`.

**Действие.**

- **Битый JSON:** файл не перезаписывается молча. Остановите профиль, сохраните
  копию, восстановите из `state.json.bak-*` (бэкап делается перед миграцией),
  либо удалите файл и выполните `/remote connect` заново (привязку придётся
  повторить).
- **Файл из будущего** (новее плагина): обновите плагин (`bin/install-remote.sh
  --update`) или восстановите старый файл из бэкапа. Плагин в этом состоянии
  работает без удалённого режима и **не перезаписывает** файл.

**Профилактика.** Обновляйте плагин до запуска новой версии состояния; бэкапы
храните рядом (`state.json.bak-<версия>-<ts>`), проверяйте `/remote doctor` после
обновления.

### Секреты не читаются

<!-- doctor-fail: credentials -->

**Симптомы.** `/remote doctor` → `credentials:<ИМЯ>` = fail «секрет не найден»;
каналы не поднимаются; `writable: false` — секрет только для чтения.

**Быстрая проверка.** `/remote doctor` (`credentials`); проверьте переменные
окружения профиля и файл секретов DSH; `/remote connect` для перевыпуска.

**Действие.** Задайте секрет через `ctx.credentials` (или переменную окружения —
она приоритетнее файла). Если `writable: false` — секрет меняйте вручную
(владелец файла), плагин его не перезапишет.

**Профилактика.** Один источник секретов на установку; после смены окружения
перезапускайте профиль; не дублируйте токен в `config`.

### Релей недоступен

<!-- doctor-fail: relay -->

**Симптомы.** Вопросы не уходят через свой сервер; `/remote doctor` → `relay` =
fail («нет связи»), в detail видны `WS: …`, число переподключений и `pending`.

**Быстрая проверка.**

```bash
curl -fsS <url релея>/healthz
/remote doctor --json   # relay: detail/action
```

**Действие.** Проверьте URL и токен релея, доступность `/healthz` (сеть, DNS,
сертификат), логи релея. Пока релей лежит, вопросы уходят в GUI (fail closed) —
сессия не зависает. После восстановления поллер переподключится сам (backoff).

**Профилактика.** Мониторьте `/healthz` и `reconnectAttempts`; держите запасной
канал (Telegram) в `config.transports`; обновляйте токен релея заранее.

### Вопрос висит: сообщение есть, ответа нет

<!-- doctor-fail: timers -->

**Симптомы.** В чате сообщение с кнопками, DSH ждёт; `/remote doctor` → `timers`
= warn/fail; `/remote stats` → `queues.timers_active` растёт, `questions.expired`
не увеличивается.

**Быстрая проверка.** `/remote status` (открытые вопросы, TTL); `/remote doctor`
(`timers` — активные и `pending`); `/remote audit 20` — были ли поздние ответы;
в журнале — `expired`/`orphan-*`.

**Действие.** Нажмите кнопку ещё раз (повторный/поздний ответ не переигрывает
решение, но виден в журнале). Если канал не отвечает — проверьте `relay`/
`getme`. TTL (по умолчанию 30 минут) снимет вопрос отказом, а не «тихим
разрешением»; `/remote doctor` → `timers` покажет, что сторож жив. Если
`healthCheck` устойчивости упал — перезапустите профиль: `pending` переживёт
рестарт, «осиротевшие» вопросы будут сняты.

**Профилактика.** Следите за `queues.timers_active` и `pending`; не отключайте
канал, пока есть открытые вопросы; гибрид (`approvals.hybrid`) отдаёт вопрос в GUI
раньше TTL — включите, если телефон не всегда под рукой.

## Чего RUNBOOK не делает

- Не хранит секретов и тел вопросов — только команды и пути.
- Не обещает «тихого» восстановления состояния: битый/будущий `state.json`
  останавливает удалённый режим, а не перезаписывается.
- Не заменяет `docs/user-guide.md` (настройка и команды) и `docs/approvals.md`
  (политика подтверждений). Протокол релея — `docs/relay/PROTOCOL.md`.
