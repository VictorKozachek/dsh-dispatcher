# Приёмка вживую: удалённое управление вопросом

Чек-лист первой живой проверки плагина `dsh-remote` в приложении DSH.
Всё, что здесь, проверяется **руками и глазами** — тесты это не покрывают:
настоящий бот, настоящий телефон, настоящее приложение.

Версия плагина на момент проверки: **0.2.0**.
Профиль: **desktop** (его читает приложение). `web`-профиль не используется.

## 0. Предусловия

```bash
bin/install-remote.sh --profile desktop --dry-run   # план
bin/install-remote.sh --profile desktop             # поставить
```

Затем **перезапустить приложение** (Cmd+Q → открыть): новый пакет читается только
при старте.

Признак, что плагин поднялся:

- появился каталог `~/.dsh/remote-control/` (в нём `state.json`);
- в правом сайдбаре «+» доступен таб **«Удалённое управление»**;
- `/remote status` в сессии отвечает, а не «неизвестная команда».

Если плагин не поднялся — сразу откат (см. §8) и смотреть лог приложения.

## 1. Бот в Telegram

1. @BotFather → `/newbot` → имя → username (обязан кончаться на `bot`).
2. Токен `123456789:AAH…` — сохранить.
3. `/setjoingroups` → **Disable** (бот не должен попадать в группы).
4. Открыть своего бота и нажать **Start** — без этого бот не может писать первым.

## 2. Привязка: `/remote connect`

В любой сессии DSH:

```
/remote connect
```

Ожидаемые шаги (каждый — локальный вопрос в GUI, потому что удалённый режим ещё
выключен):

| Шаг | Что выбрать/ввести | Ожидаемо |
|---|---|---|
| транспорт | **Telegram** | предложен следующий шаг |
| токен | `123456789:AAH…` | «токен сохранён» (в `~/.dsh/.credentials.yaml`, не в git) |
| привязка | отправить боту показанный 6-значный код | «✅ Привязано: @бот · chat … · user …» |

Проверки: токен виден в `/remote status` **маской**, не целиком; в
`~/.dsh/remote-control/state.json` токена нет.

## 3. Включение и тест

```
/remote on        # для этого проекта; --all — для всех
/remote test      # в Telegram должно прийти тестовое сообщение
/remote doctor    # все проверки ok, код возврата 0
```

Ожидаемо: сообщение в Telegram с шапкой проекта; `doctor` — `ok` по токену,
`getMe`, поллеру, каналу и состоянию.

## 4. Сквозной сценарий (главное)

1. Попросить агента задать вопрос: «задай мне вопрос через ask_user_question,
   например подтверди удаление ветки».
2. **Вопрос должен прийти в Telegram** (в GUI его быть не должно — режим `remote-only`):
   ```
   ▸ dsh-dispatcher · worker · 18:41 · до 19:11
   Удалить ветку feature/001 после слияния?
   [ Да, удалить ] [ Оставить ] [ Другой ответ… ]
   ```
3. Нажать кнопку на телефоне → сообщение правится в «✅ Отвечено: …», кнопки снимаются.
4. Агент **продолжает шаг** (не новый турн) — в сессии видно результат
   `ask_user_question` с выбранным вариантом.
5. Повторить со свободным ответом («Другой ответ…» → текст) и с двумя вопросами
   одновременно (проверка роутинга).

## 5. Прозрачность и диагностика

```
/remote status      # привязка, включённые проекты, режим
/remote stats       # метрики: спрошено/отвечено, латентность
/remote audit 5     # последние решения, кто ответил и когда
/remote doctor --json   # машинный отчёт
```

## 6. Проверка отказов

| Сценарий | Ожидаемо |
|---|---|
| `/remote off`, затем вопрос | вопрос в GUI, в Telegram ничего |
| ответ из чужого аккаунта боту | игнорируется, в лог — «чужой user id» |
| ответ на уже закрытый вопрос | «вопрос закрыт», исход не меняется |
| Telegram недоступен (выключить VPN/сеть) | вопрос уходит в GUI через ~30 с |
| не отвечать до TTL | напоминание за 5 мин; по истечении — `onExpire` (по умолчанию отказ) |
| перезапуск приложения с открытым вопросом | сообщение правится «сессия перезапущена, вопрос снят» |

## 7. Что записать в карточку/заметки

- id сессии оркестратора и исполнителя, номера сообщений в Telegram;
- скриншоты: вопрос с кнопками, ответ, `/remote doctor`;
- время от вопроса до ответа (по `/remote stats`);
- любые расхождения с этим чек-листом — дословно.

## 8. Откат (если что-то пошло не так)

```bash
bin/install-remote.sh --profile desktop --uninstall   # убрать из профиля
# перезапустить приложение — плагин больше не поднимается
```

`--uninstall` идемпотентен и не трогает чужие зависимости/бандлы профиля;
он проверен на временном `DSH_HOME` (установка → удаление → повторное удаление).

Данные плагина остаются в `~/.dsh/remote-control/` — при необходимости удалить
вручную; токен — `unset` через `/remote disconnect` или убрать
`DSH_REMOTE_TELEGRAM_TOKEN` из `~/.dsh/.credentials.yaml`.

## Локальный релей без телефона (задача 040)

Цель: убедиться, что плагин публикует вопрос в **свой** релей и получает ответ
через API — без хостинга, TLS и телефона. Всё только на `127.0.0.1`.

1. Собрать и запустить релей (точные команды — `relay/README.md`,
   «Проверенная локальная последовательность»):

   ```bash
   cd relay
   export CARGO_HOME="$PWD/../.cargo-home" CARGO_TARGET_DIR="$PWD/../.cargo-target"
   cargo build
   RELAY_BIND=127.0.0.1:8080 RELAY_AGENT_TOKEN=dev-agent-token \
   RELAY_DATABASE_URL="sqlite://$PWD/.run/relay.db?mode=rwc" \
     "$CARGO_TARGET_DIR/debug/dsh-relay"
   curl -sS -H 'X-Relay-Version: 1' http://127.0.0.1:8080/healthz   # ok:true
   ```

2. Smoke самого релея:

   ```bash
   RELAY_BASE_URL=http://127.0.0.1:8080 RELAY_AGENT_TOKEN=dev-agent-token \
     deploy/smoke.sh
   # smoke: OK — healthz, привязка, вопрос, ответ, идемпотентность
   ```

3. Плагин → релей (без телефона). В `dsh-remote` транспорт `relay` — это обычный
   `createRelayTransport`; в сессии он поднимается после
   `/remote connect` → **Relay** → `http://127.0.0.1:8080` + токен агента.
   Для проверки без GUI/телефона тот же транспорт подключается скриптом:

   ```js
   const transport = createRelayTransport({ url: "http://127.0.0.1:8080", agentToken: "dev-agent-token" });
   await transport.start();                       // healthCheck + long-poll/WS
   const answerer = createAnswerer({ transport, registry });
   answerer.attach(ctx);
   const pending = answerer.handler({ questions: [{ id: "live-q", question: "Продолжать?", options: [{ label: "Да" }, { label: "Нет" }] }], agent: { id: "live" } }, () => next());
   // устройство (iOS или curl) регистрируется и отвечает:
   // POST /v1/answers {questionId, selected:["o1"], idempotencyKey}
   const result = await pending;                  // {answers:[{selected:["Да"]}]}
   ```

   Ответ приходит через тот же long-poll/WS, что и у живого телефона; `next()`
   не вызывается. Проверено вживую: вопрос появился в `GET /v1/questions`,
   `POST /v1/answers` вернул `201`, сессия получила `selected: ["Да"]`.

4. Недоступный релей (порт закрыт): `createRelayTransport` с
   `http://127.0.0.1:9`, тот же `answerer.handler` → `next()` вызывается за
   десятки миллисекунд (вопрос уходит в GUI), ожидание не висит.

Ограничения: e2e-шифрование (021) для этого прогона выключено (открытый режим);
webhook, TLS и внешний хостинг — задача 041.

Найдено и исправлено по ходу приёмки (каждое — отдельный дефект, а не переделка):

1. `commands` падал: прямой доступ к `ctx.commands` без `inject` (cordis бросает).
2. Секреты искались один раз на старте — сервис `credentials` монтируется позже.
3. Фичи, ждавшие `remoteTransport`, не поднимались после привязки (повторный проход).
4. Канал не поднимался, если секреты ещё не смонтированы (повторы через 1/3/7/15 с).
5. Тесты читали живое состояние и поднимали второй поллер (`DSH_HOME` теперь уважается).
6. Вопрос без вариантов не имел поля ввода в Telegram (`force_reply`).

Открытый дефект: пачка вопросов (`bug/037`). До исправления агентам в этом проекте

## Туннель и телефон (задача 041)

Живая проверка 2026-11-11, macOS arm64, релей `relay/` (cargo build), плагин и
клиент — на фейковом/реальном HTTPS-туннеле. Хостинг не использовался.

| Шаг | Результат |
|---|---|
| `cargo build` релея | ✅ собрался; `dsh-relay` слушает `127.0.0.1:8080` |
| `curl /healthz` локально | ✅ 200, миграции применены |
| `deploy/smoke.sh` против `127.0.0.1:8080` | ✅ OK (привязка, вопрос, ответ, идемпотентность) |
| Cloudflare quick tunnel (`cloudflared --url … --protocol http2`) | ⚠️ HTTPS-адрес выдан, первый `/healthz` — 200, дальнейшие запросы 502/530 (нестабильный quick tunnel в этой сети); для приёмки взят другой туннель |
| SSH-туннель `localhost.run` (`ssh -R 80:127.0.0.1:8080 nokey@localhost.run`) | ✅ `https://<id>.lhr.life` → `/healthz` 200 |
| `deploy/smoke.sh` через HTTPS-туннель | ✅ healthz, код привязки, устройство, привязка, вопрос, ответ, идемпотентный повтор |
| Клиент RelayKit (тот же код, что в iOS-приложении) через HTTPS-туннель | ✅ `PAIRED deviceId=…`, `QUESTION id=…`, `ANSWERED questionId=… selected=o1` |
| Агент читает ответ через HTTPS-туннель | ✅ `GET /v1/answers?questionId=…` → 200, `selected:["o1"]` |
| Приложение на телефоне (UI) | ⚠️ не проверялось: физического устройства в сессии нет; проверен клиент RelayKit (привязка/вопрос/ответ), который использует то же приложение |

Туннель-адрес одноразовый (после проверки процесс остановлен, адрес недействителен).
Для телефона нужен HTTPS (cleartext-HTTP допустим только для `127.0.0.1`/LAN);
при смене адреса туннеля приложение перепривязывается по новому `pairCode`.
